# ชุดโจทย์ Week 2 · e-Service กลางของ "เทศบาลนครตัวอย่าง"

โจทย์ร่วมของทุกกลุ่ม: สร้างระบบ **e-Service กลาง** ให้เทศบาลสมมติ ประชาชนยื่นคำขอ 3 บริการและจ่ายเงินออนไลน์ เจ้าหน้าที่ตรวจและออกเอกสารดิจิทัล หัวหน้าอนุมัติ ผู้บริหารดู Dashboard ผู้ตรวจสอบดู Audit Trail แล้ว **พิสูจน์ด้วย Playwright** ว่าเว็บที่ agent สร้างทำตามกฎจริง ไม่ใช่แค่ "AI บอกว่าทำแล้ว"

> หน่วยงานเป็นของสมมติ ห้ามใช้ชื่อ ตรา หรือโลโก้หน่วยงานจริงในเว็บ
> ThaiD, PromptPay QR และลายเซ็นดิจิทัลในชุดนี้เป็น **ตัวจำลอง** ทั้งหมด ไม่เชื่อมระบบจริง

## 1. ไฟล์ในชุดและลำดับการอ่าน

| ลำดับ | ไฟล์ | ใช้ทำอะไร |
|---|---|---|
| 0 | `brief/BRIEF.md` | โจทย์ต้นทางจากผู้สอน (แหล่ง [D]) อ่านไว้ แก้ไม่ได้ |
| 1 | `USER-STORIES.md` | 14 เรื่องราวผู้ใช้ + เกณฑ์ยอมรับ + ข้อที่โจทย์ยังไม่ชัดและที่เราสมมติ |
| 2 | `REQUIREMENTS.md` | FR / BR (กฎมีตัวเลข + ค่าขอบ) / NFR + แผนภาพสถานะ + สมมติฐาน A-xx + คำถามถึงหน่วยงาน Q-xx |
| 3 | `CONTRACT.md` | **สัญญา** ที่ทุกเว็บต้องทำตาม: route, `data-testid`, ข้อความ error, API, test hook |
| 4 | `TEST-DATA.md` | ข้อมูล seed ที่เว็บต้องสร้างหลัง reset + ไฟล์ทดสอบ |
| 5 | `TEST-PLAN.md` | 51 test case กลาง (ผลที่คาดหวังเป็นตัวเลข/ข้อความตรงตัว) |
| 6 | `BUGS.md` | `BUG_MODE` 12 บั๊ก และวิธีพิสูจน์ว่า test จับได้ |
| 7 | `PROMPTS.md` | พรอมต์ทีละขั้นสำหรับคัดลอกไปวาง |

ลำดับที่แนะนำ: README → USER-STORIES → REQUIREMENTS → CONTRACT → TEST-DATA → สร้างเว็บ → TEST-PLAN → BUGS

## 2. สิ่งที่นักเรียนต้องทำใน Week 2

| ขั้น | ทำอะไร | ได้อะไร |
|---|---|---|
| 1 | อ่าน USER-STORIES / REQUIREMENTS / CONTRACT / TEST-DATA ให้ครบ แล้วให้ `dag-planner` แตกงานเป็นกราฟ (ใครสร้างอะไร ก่อน-หลัง ไฟล์ไหนชนกัน) | แผนงานแบบ DAG |
| 2 | ให้ `agent-team` สร้างเว็บตาม REQUIREMENTS + CONTRACT + TEST-DATA | เว็บที่รันได้ พร้อม seed |
| 3 | เปิดเว็บด้วย `TEST_MODE=1` แล้วรัน TEST-PLAN ด้วย Playwright (เขียนสคริปต์ test เองหรือให้ agent เขียนจากการ์ด TC · หลัง `reset` ทุกครั้งต้องล็อกอินใหม่) | รายงาน 51 TC ต้องผ่านครบ |
| 4 | เปิด `BUG_MODE` ทีละบั๊ก (B01–B12) แล้วรันชุดเดิมซ้ำ | พิสูจน์ว่า TC ที่ระบุล้ม และที่เหลือผ่าน |
| 5 | ทำตาราง triage ตาม `BUGS.md` | หลักฐานว่า test จับบั๊กได้จริง |

**พรอมต์ทุกขั้นสำหรับคัดลอกไปวาง อยู่ใน [`PROMPTS.md`](PROMPTS.md)** (ขั้น 0 เอาชุดโจทย์เข้า container → 1 วางแผน → 2 ตรวจแผน → 3 รันจริง → 4 รัน TEST-PLAN → 5 BUG_MODE)

## 3. กติกา

| ข้อ | กติกา |
|---|---|
| 1 | ใช้ stack อะไรก็ได้ (Node, Python, PHP, …) |
| 2 | **ต้องทำตาม CONTRACT ทุกข้อ** ได้แก่ route, `data-testid`, ข้อความ error ตรงตัวอักษร, API และ test hook ถ้าไม่ครบ test plan กลางใช้ไม่ได้ |
| 3 | ตัวเลข กฎ และข้อมูล seed ต้องตรง REQUIREMENTS + TEST-DATA ห้ามปรับเอง ถ้าเห็นว่ากฎไม่สมเหตุสมผลให้จดเป็นคำถาม ไม่ใช่แก้เงียบ ๆ |
| 4 | `TEST_MODE=1` เปิด test hook, ไม่ตั้ง = ปิด · `BUG_MODE=B03,B07` เปิดบั๊กตามรหัส (ไม่ตั้ง = เว็บถูกต้อง 100%) |
| 5 | เวลาในระบบใช้ Asia/Bangkok (+07:00) และอ่านจากนาฬิกาทดสอบ ห้ามเรียกเวลาเครื่องตรง ๆ ในกฎธุรกิจ |
| 6 | ห้ามใส่ชื่อ/ตรา/โลโก้หน่วยงานจริง ห้ามเชื่อมระบบจริง (ThaiD, ธนาคาร, CA) |

## 4. ป้ายที่มา

| ป้าย | ความหมาย |
|---|---|
| **[D]** | มาจากโจทย์ผู้สอน (`brief/BRIEF.md`) ระบุหัวข้อที่มาไว้เสมอ |
| **[R]** | กฎทั่วไป คณิตศาสตร์ หรือมาตรฐาน (เช่น checksum เลขบัตร, WCAG) |
| **⚠️A-xx** | TA สมมติเพื่อให้ทดสอบได้ ต้องส่งเป็นคำถามถึงหน่วยงาน (ดู Q-xx ใน REQUIREMENTS) |

## 5. ตัวจำลอง (ไม่ใช่ของจริง)

| ของจริง | ในชุดนี้ |
|---|---|
| ThaiD / SSO ภาครัฐ | กรอกเลขบัตร 13 หลัก + OTP `123456` (ล็อกอินเจ้าหน้าที่ใช้ username/รหัสผ่านจาก seed) |
| PromptPay | QR จำลอง + `POST /api/test/payments/<ref>/pay` แทนธนาคาร |
| ลายเซ็นดิจิทัลตาม พ.ร.บ.ธุรกรรมฯ / CA | HMAC-SHA256 ด้วยคีย์ทดสอบ |

## 6. เริ่มใช้งานอย่างเร็ว

```text
TEST_MODE=1 BUG_MODE= <คำสั่งรันเว็บของกลุ่ม>      # เว็บถูกต้อง รัน TEST-PLAN ต้องผ่านหมด
TEST_MODE=1 BUG_MODE=B03 <คำสั่งรันเว็บของกลุ่ม>    # เปิดบั๊กทีละตัว TC ที่ระบุใน BUGS.md ต้องล้ม
```

ทุก TC เริ่มด้วย `POST /api/test/reset` (ล้าง + seed ใหม่ + นาฬิกา = `2026-12-01T09:00:00+07:00` วันอังคาร) แล้วจึงตั้งนาฬิกาเพิ่มด้วย `PUT /api/test/clock`
