ขั้นนี้ไม่ได้เขียน test case แต่กำหนด **ภารกิจสำรวจ (charter)** ให้ผู้สำรวจแต่ละคนออกไปหาสิ่งที่ test case 79 ข้อยังไม่ได้คิดถึง แล้วจดผลลง `08_exploration/`

รูปแบบ charter: **สำรวจ** _อะไร_ **ด้วย** _เครื่องมือหรือข้อมูลอะไร_ **เพื่อค้นหา** _ข้อมูลหรือความเสี่ยงอะไร_

### CH-01 · สูตรโอกาสและการสุ่ม

**สำรวจ** โอกาสของแต่ละร้านและ `POST /api/draw`
**ด้วย** การผสมตัวคูณหลายตัวพร้อมกัน (โหวตแนว + โหวตร้าน + กินแล้ว + ขี้เกียจเดิน + คะแนนแมว + น้ำหนัก) และการสุ่มซ้ำหลายร้อยครั้ง
**เพื่อค้นหา** จุดที่ % บนจอไม่ตรงกับสูตร หรือผลสุ่มจริงไม่ตรงกับ % ที่แสดง

แนวคิดที่ควรลอง
- คิด % ด้วยมือ (หรือสคริปต์) จากสูตรใน `src/lib/odds.ts` แล้วเทียบกับจอ
- โหวต − หลายครั้งจนชนพื้น ×0.1
- น้ำหนักต่ำสุด 0.5 และสูงสุด 5 ร่วมกับตัวคูณอื่น
- ร้านที่ไม่มี `walkDistance` (ใช้ระยะเส้นตรง × 1.3) ในโหมดขี้เกียจเดิน
- สุ่ม 500–1,000 ครั้งผ่าน API แล้วดูว่าความถี่ใกล้ % หรือไม่
- ส่ง `scores` / `picks` แปลก ๆ ให้ `/api/draw` (เช่น 99, −99, string, แนวที่ไม่มี)

### CH-02 · ห้องและ realtime

**สำรวจ** ห้อง (`/room/CODE`) และ `GET /api/events`
**ด้วย** หลายเบราว์เซอร์ / หลาย request พร้อมกัน การตัดและต่อ SSE ใหม่
**เพื่อค้นหา** จุดที่สมาชิกเห็นข้อมูลไม่ตรงกัน หรือข้อมูลหายเมื่อทำพร้อมกัน

แนวคิดที่ควรลอง
- 2–5 คนโหวตแนวเดียวกันพร้อมกัน (ยิง request ขนาน) แล้วดูว่าผลรวมถูกไหม
- รหัสห้องตัวพิมพ์เล็ก / มีช่องว่าง
- ชื่อเล่นว่าง ยาว 25+ ตัว อีโมจิ ช่องว่างล้วน ชื่อเดียวกันต่างตัวพิมพ์
- สุ่มร้านในห้องพร้อมกันสองคน
- ต่อ SSE แล้วดู event แรก / ตัดแล้วต่อใหม่
- สมาชิกห้องหนึ่งโหวตในอีกห้อง

### CH-03 · ข้อมูลร้าน ประเภทอาหาร และ API

**สำรวจ** `PATCH/DELETE /api/restaurants/:id`, `POST /api/restaurants`, `/api/categories`, `PUT /api/restaurants/:id/rating`
**ด้วย** ค่าขอบเขต ค่าผิดชนิด ข้อความยาว ตัวอักษรพิเศษ และลำดับการกระทำที่ไม่ปกติ
**เพื่อค้นหา** ข้อมูลที่ระบบรับทั้งที่ไม่ควรรับ ข้อมูลเสียหลังลบ/แก้ และความเสี่ยงจากการไม่มี login

แนวคิดที่ควรลอง
- `baseWeight` 0.49 / 0.5 / 0.74 / 5 / 5.01 / "2" / null
- ชื่อร้าน / ชื่อเล่น / ชื่อแนวที่มี `<script>`, HTML, อีโมจิ, 81 ตัวอักษร
- เพิ่มร้านที่ระยะ 1,999 / 2,001 ม. พิกัดผิดรูปแบบ ลิงก์ Google Maps หลายแบบ
- ลบประเภทอาหารที่เป็นแนวเดียวของร้าน แล้วร้านนั้นเป็นอย่างไร
- แก้ชื่อแนวให้ซ้ำแนวอื่น · ลบแล้วเพิ่มชื่อเดิมกลับมา
- ให้คะแนนด้วย `rater` สั้น/ยาว/ตัวอักษรไม่อนุญาต · score 0–5
- เขียนพร้อมกันหลาย request แล้วดูว่าไฟล์ข้อมูลยังถูกต้อง

### CH-04 · หน้าจอ มือถือ แผนที่ ประวัติ

**สำรวจ** หน้า `/`, `/history`, `/restaurants/new`, `/categories`, มุมมองแผนที่
**ด้วย** Playwright (Chromium) บนจอ 1440×1000 และ 390×844, คีย์บอร์ดอย่างเดียว, บล็อกอินเทอร์เน็ตภายนอก
**เพื่อค้นหา** ปัญหาการใช้งาน การเข้าถึง (accessibility) ข้อความ และสถานะที่หน้าจอแสดงผิด

แนวคิดที่ควรลอง
- ใช้ Tab / Enter อย่างเดียวสุ่มร้านและโหวตได้ไหม · ปุ่มมีชื่อให้โปรแกรมอ่านจอไหม
- จอมือถือ: ข้อความล้น ปุ่มเล็กเกินกด แผนที่ใช้ได้ไหม
- กดสุ่มร้านรัว ๆ หลายครั้ง
- ตัวกรองที่ไม่เหลือร้าน แล้วสลับไปแผนที่
- ประวัติเมื่อร้านที่เคยสุ่มได้ถูกปิด / ถูกลบ
- ตัวเลข % ที่ปัดเศษ เช่น `<0.1%` รวมกันได้ 100% หรือไม่

## 3. กติกาสำหรับผู้สำรวจทุกคน

1. ใช้เฉพาะเซิร์ฟเวอร์ของตัวเอง ห้ามแตะพอร์ต 3100 (เซิร์ฟเวอร์ dev ของเจ้าของ) และห้ามแก้ไฟล์ใน `src/`, `data/`, `e2e/`
2. เริ่มทุกการทดลองด้วย `POST /api/test/reset`
3. จดทุกอย่างที่เจอ แม้ไม่แน่ใจว่าเป็นบั๊ก แยกเป็น **บั๊ก** / **คำถาม** / **ข้อสังเกต**
4. ทุกข้อต้องมีขั้นตอนทำซ้ำ ผลที่ได้ และผลที่คาด (อ้าง story หรือโค้ดที่เกี่ยวข้อง)
5. ใส่ระดับที่เสนอ (P1/P2/P3) ตามเกณฑ์ใน `10_TEST-PLAN.md` ผู้ตัดสินในขั้นที่ 9 จะยืนยันอีกครั้ง
6. หมดเวลาแล้วหยุด เขียนสรุปว่าสำรวจอะไรไปแล้ว อะไรยังไม่ได้แตะ
