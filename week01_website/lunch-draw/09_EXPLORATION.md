## 1. สรุป

ผู้สำรวจ 4 คนส่งข้อพบมา 48 ข้อ ผมทำซ้ำแล้ว **ยืนยันได้ 28 ข้อ (master)** **ซ้ำ 13 ข้อ** (รวมเข้า master แล้ว) **ไม่ยืนยัน 2 ข้อ** และ **เป็นคำถามถึงทีม 5 ข้อ** มี **P1 สองข้อ** ซึ่งตรงกับความกลัวหลักของทีมทั้งสองเรื่อง
**(1) สมาชิกในห้องเห็นผลสุ่มคนละร้าน** เมื่อ 2 คนกด "สุ่มร้าน" พร้อมกัน ผมทำซ้ำได้ **3/3 รอบในเบราว์เซอร์จริงโดยไม่ต้องหน่วงเน็ต** ข้อนี้หนักกว่าที่ CH-02 รายงาน เพราะ CH-02 ใช้สคริปต์จำลอง client และสรุปว่า "จอสุดท้ายตรงกันทุกรอบ" (F02-03) ซึ่งไม่จริงในเบราว์เซอร์
**(2) เลขร้านถูกใช้ซ้ำหลังลบร้านที่เพิ่มเอง** ร้านใหม่ได้คะแนนแมว โทษ "กินแล้ว" และโหวตในห้องของร้านเก่าไปด้วย และหน้าประวัติเปลี่ยนชื่อร้านย้อนหลัง
P2 มี 5 ข้อ ได้แก่ กดสุ่มรัวแล้วได้หลาย draw, โทษกินแล้วหายเมื่อสุ่มครบ 1,000 ครั้ง, ลบประเภทอาหารแล้วร้านไม่เหลือประเภท, response โหวตที่มาช้าทับข้อมูลห้อง และโหวตที่ล้มเหลวแต่จอแสดงว่าสำเร็จ
ผมลดระดับ 3 ข้อจาก P2 เป็น P3: F04-02 (เกิดเฉพาะเมื่อร้านอันดับต้นมีชื่อไทยยาวไม่มีช่องว่าง ข้อมูลตั้งต้นไม่เกิด), F03-13 (ลิงก์เส้นทางพบไม่บ่อย และหมุดตัวอย่างบนฟอร์มแสดงตำแหน่งให้เห็น) และ F03-03 (ส่วนที่เป็นบั๊กเกิดเฉพาะเมื่อลบครบทุกประเภท ส่วนเรื่อง undo ย้ายไปเป็นคำถาม)

## 3. รายการบั๊กที่ยืนยันแล้ว (master list)

### P1

**EXP-01 · สองคนกดสุ่มพร้อมกันในห้องแล้วจอเห็นคนละร้าน** (F02-01, F02-03)
- ทำซ้ำ: เปิดห้อง → A, B, C เข้าห้องคนละเบราว์เซอร์ → A กับ B กด "สุ่มร้าน" พร้อมกัน → รอแอนิเมชันจบ
- คาด: ทุกจอแสดง `latestDraw` ของห้อง · ได้: จอใดจอหนึ่งค้างที่ draw ของตัวเอง (3/3 รอบ แม้ไม่หน่วงเน็ต) และไม่แก้ตัวเองจนกว่าจะมีคนสุ่มใหม่
- สาเหตุ: `runDraw()` เรียก `reveal(json, odds)` ด้วย response ของตัวเองเสมอ (`lunch-app.tsx:338-339`) ทั้งที่ SSE อาจส่ง draw ที่ใหม่กว่ามาก่อนแล้ว ประกอบกับ `reveal()` (`:179-199`) ไม่ยกเลิก timer ของรอบก่อน การ์ดจึงจบที่ร้านที่ timer มาถึงทีหลัง และ server ไม่กันการสุ่มซ้อน
- แก้: ในห้อง ให้แสดงผลเฉพาะ `latestDraw` ที่มาจาก SSE หรือ GET (ไม่ใช้ response ของ POST) และ `reveal` ต้อง clear timer เก่า · ทางเลือกเพิ่ม: server ปฏิเสธการสุ่มที่ห่างจากครั้งก่อนไม่ถึง N วินาที

**EXP-02 · ลบร้านที่เพิ่มเองแล้วเพิ่มร้านใหม่ ร้านใหม่ได้เลขเดิมและรับข้อมูลของร้านเก่าไปทั้งหมด** (F03-01, F02-04, F04-03)

**EXP-06 · response ของโหวตที่มาช้าทับ state ห้องที่ใหม่กว่า** (F02-02)
- ทำซ้ำ: A โหวต (response ช้า 1.5 วินาที) แล้ว B โหวตอีกประเภทระหว่างนั้น · คาด: จอ A ตรงกับ server · ได้: A เห็นข้าวแกง = 0 แต่ server = 1 และค้างจนกว่าจะมี event ถัดไป (% บนกระดานของ A ผิด แต่ผลสุ่มยังถูกเพราะ server ใช้ข้อมูลของตัวเอง)

**EXP-07 · โหวตที่ล้มเหลวยังแสดงว่าสำเร็จ ไม่มีข้อความแจ้ง** (F02-08)

## 5. ความครอบคลุม: สิ่งที่ทั้ง 4 charter ยังไม่ได้สำรวจ

- **ไฟล์ข้อมูลเสียหรือถูกแก้จากข้างนอก** (ความเสี่ยงสูง): ถ้าตอนเริ่ม `restaurants.json` parse ไม่ได้ `readJson` จะคืน `[]` (`store.ts:86-92, 110`) และการเขียนครั้งถัดไปจะทับไฟล์ด้วยรายการว่าง นอกจากนี้ NFR-07 บอกว่า "แก้ไฟล์จากข้างนอกแล้วโหลดใหม่เอง" แต่โค้ดโหลดใหม่เฉพาะ `restaurants.json` ส่วน categories / ratings / state ไม่โหลดใหม่ (`store.ts:121-128`) ทั้งสองเรื่องยังไม่มีใครทดสอบจริง
- **เวลา**: ตัวคูณกินแล้วระหว่างวันที่ 1–7 (BR-06), ห้องหมดอายุ 3 วัน (BR-24), ป้าย "รอยืนยัน" ภายใน 2 ชม. (BR-26), เขตเวลา Asia/Bangkok เมื่อ server อยู่คนละโซน (NFR-12) ยังไม่ได้ทดสอบด้วย fake clock
- **Q2 `openingHours`** และ **FR-22 ดึงข้อมูล OSM ใหม่** (เลขร้านต้องไม่เปลี่ยน และค่าที่ทีมแก้ต้องไม่ถูกทับ) ยังไม่มี charter ไหนแตะ
- **บริการระยะเดินจริง (OSRM)** และ timeout 4 วินาที (NFR-02) ถูกข้ามในโหมดทดสอบ · ยังไม่ได้วัดประสิทธิภาพตาม NFR-01/02 (2 วินาที / 300 ms)
- **ฟีเจอร์ค้นหา (TC-SEARCH-\*)** ไม่อยู่ใน charter ไหนเลย
- **realtime ในระยะยาว**: server รีสตาร์ตแล้ว EventSource ต่อใหม่เองไหม, listener รั่วเมื่อเปิดปิดแท็บจำนวนมาก, หลาย process (NFR-08)
- **ห้องบนมือถือ**, หน้า JoinRoom และฟอร์ม `/restaurants/new` ด้วยคีย์บอร์ด, การปักหมุดด้วยคีย์บอร์ด
- **โปรแกรมอ่านจอจริง** (NVDA / VoiceOver), `prefers-reduced-motion` (NFR-11 กำหนดไว้ แต่ยังไม่ได้ตรวจ), ซูม 200%, โหมดสว่าง/มืด
- **เบราว์เซอร์อื่น** นอกจาก Chromium (Safari บน iPhone ซึ่งทีมน่าจะใช้มาก, Firefox)
- แก้ร้านหรือลบประเภทระหว่างที่ห้องกำลังสุ่ม (race ระหว่าง edit กับ draw) และกด "ไปกิน" / ยกเลิกพร้อมกันหลายคน
- ขนาดหมุดตามโอกาสบนแผนที่ (FR-09) เทียบกับ % · หมุดซ้อนกัน "ร้านในจุดเดียวกัน" บนมือถือ
